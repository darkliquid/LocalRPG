# Route and DTO Manifest Design

**Date:** 2026-09-28
**Status:** Implemented (routes) on 2026-09-28; the DTO-name guard is **rejected**.

**DTO guard rejected (2026-09-28).** The inventory shows the two sides share
almost no names: of 60 exported Go types, only 3 match `frontend/src/types.ts`
exactly (`CharacterPortraitDTO`, `TurnEvent`, `LimitsDTO`). Everything else is
renamed (`PlayerDTO`→`PlayerState`, `EntityDTO`→`EntityNote`,
`SegmentDTO`→`TurnSegment`) or exists on one side only (TS has `ExportJob`,
`PathsConfig`, `GenerateCharacterRequest`; Go has `MergeEntityRequestDTO`,
`STTResponse`, `RequestCheckDTO`). A real guard needs an alias map plus
Go-only/TS-only exemption lists, which would rot, to catch the weaker of the two
drifts: the route guards already catch path drift, and `tsc` catches a missing
import. Deriving `types.ts` from the Go DTOs is the only version worth doing, and
it is a separate ambition.
**Scope:** Make the API route table data rather than imperative registrations, check it in, and fail a test when the frontend drifts from it
**Related:** `pkg/gui/server.go`, `pkg/gui/types.go`, `frontend/src/api/client.ts`, `frontend/src/types.ts`; implements finding P2.8 of `docs/architecture/review-2026-09-24.md`

## 1. Overview & Goals

The API surface is defined three times by hand: `registerRoutes` mounts handlers
(`pkg/gui/server.go`), `routePattern` names spans for those paths (`server.go`),
and `frontend/src/api/client.ts` re-spells every path in `fetch` calls, with
`frontend/src/types.ts` mirroring the Go DTOs. Twenty-six mounts plus one asset
handler are registered today, and the client exposes 56 methods. The review
flagged this as P2.8: nothing fails when the two sides drift, and a renamed path
or a new DTO is discovered at runtime.

**Goals:**

- One source of truth for the mounted route patterns.
- A checked-in manifest that a test regenerates and compares, so drift is a test
  failure with a diff rather than a 404 in the app.
- A check that every `/api/...` literal the frontend calls resolves to a
  registered mount.
- A check that `routePattern` names every mount, so span names never fall back to
  `http.request` by accident.

**Non-Goals:**

- Generating the frontend client or DTO types wholesale (recorded as Open
  Questions).
- Extracting per-method sub-routes from the method-branching handlers; the mount
  is the unit here.
- Changing any route, DTO, or response shape.

**Success Criteria:**

- `routes` is a Go table that `registerRoutes` iterates; adding a route is one
  line.
- `go test ./pkg/gui -update-routes` regenerates the manifest; without `-update`,
  a stale manifest fails with the added/removed rows.
- A test fails if `client.ts` calls `/api/...` and no mount covers it.
- A test fails if a mount is not covered by `routePattern`.
- A test fails if the manifest lists a mount the server does not register.

## 2. Investigation Findings

- `registerRoutes` (`pkg/gui/server.go:84-118`) registers 26 `HandleFunc` mounts
  plus an optional `Handle("/", assetServer)`; the list is imperative and ordered
  by hand.
- `routePattern` (`server.go:50-82`) is a separate switch that names spans. It
  already special-cases `/api/models`, `/api/game/`, `/api/system/`,
  `/api/world/`, `/api/audio/`, `/api/docs`, and recently `/api/export`; a mount
  with no case silently becomes `"http.request"`.
- Handlers branch on method and subpath internally (for example
  `handleGameRoutes`, `handleExportRoutes`), so the mount — not the endpoint — is
  the addressable unit both sides can agree on.
- `frontend/src/api/client.ts` builds URLs with template literals
  (`/api/game/${gameID}/...`) and static strings; `EventSource` is used for
  `/api/models/events` and `/api/export/events`.
- There is no `go:generate` anywhere in the repository and no codegen step in
  `mise.toml`; the docs catalogue is generated by a test with `-update-docs`,
  which is the established pattern to follow.
- `frontend/src/types.ts` mirrors the Go DTOs by hand and is checked only by
  `tsc`.

## 3. Design

### 3.1 The route table

```go
// pkg/gui/routes.go
type routeMount struct {
    Pattern string // the mux pattern, e.g. "/api/game/"
    Handler string // the server method, for the manifest only
}

// mounts is the single list of API mounts. registerRoutes iterates it.
var mounts = []routeMount{
    {"/api/game/", "handleGameRoutes"},
    {"/api/games", "handleGamesRoutes"},
    // ...
    {"/api/export", "handleExportRoutes"},
    {"/api/export/", "handleExportRoutes"},
    // ...
}

// Routes returns the mounted API patterns, sorted, for the manifest and tests.
func Routes() []string
```

`registerRoutes` becomes a loop that binds each pattern to its handler via a
`map[string]http.HandlerFunc`, so the handler name is resolved in one place and
the table stays declarative. `routePattern` is extended (and tested) to cover
every mount.

### 3.2 Checked-in manifest and regeneration

Follow the docs pattern:

- `pkg/gui/testdata/routes.json` holds the sorted mount patterns.
- `go test ./pkg/gui -update-routes` writes it.
- `TestRouteManifestIsCurrent` reads it and compares; a mismatch prints the
  added/removed rows and the regeneration command.
- `TestRoutePatternNamesEveryMount` calls `routePattern(mount)` for each mount and
  asserts it is not `"http.request"`.
- `TestEveryRegisteredMountIsInTheManifest` asserts the loop bound exactly the
  table (no stray `HandleFunc` outside the table), by comparing against the set
  the server actually registers (expose a package-level
  `registeredMounts(*Server) []string` used only by tests, or assert the loop
  length).

### 3.3 Frontend drift check

A Go test parses `frontend/src/api/client.ts` for string literals beginning
`/api/` (both static strings and the leading literal of a template) and resolves
each against the mount table:

- exact match, or
- the literal is under a trailing-slash mount (`/api/game/` covers
  `/api/game/${id}/turn`).

A literal with no covering mount fails with its line. This catches a typo or a
removed route before the app does. The reverse direction (a mount the client
never calls) is reported as a warning list rather than a failure, because some
mounts are intentionally server-only (`/api/docs`, the asset handler).

### 3.4 DTO contract (lighter)

A full DTO generator is a separate effort. The first step is a checked list of the
DTO type names the client depends on: the test extracts exported type names from
`pkg/gui/types.go` and from `frontend/src/types.ts` and asserts every interface
the client imports from `types.ts` exists. This catches a deleted or renamed DTO
without generating code.

## 4. Interfaces

```go
// pkg/gui
type routeMount struct{ Pattern, Handler string }
func Routes() []string   // sorted mount patterns
// routePattern stays internal; covered by its test.
```

Test flags: `-update-routes` (mirrors `-update-docs`).

## 5. Error Handling

| Situation | Behaviour |
| --- | --- |
| Manifest stale | Test fails, prints the diff and the regenerate command |
| Frontend calls an unknown path | Test fails with file:line |
| Mount missing from `routePattern` | Test fails naming the mount |
| Mount added to the table, no handler | Compile error at the handler map |
| Client never calls a mount | Reported as a warning list, not a failure |

## 6. Testing & Verification

Go (stdlib `testing`):

- `TestRouteManifestIsCurrent` (with `-update-routes` regeneration).
- `TestRoutePatternNamesEveryMount`.
- `TestEveryRegisteredMountIsInTheManifest`.
- `TestFrontendPathsResolveToMounts` (seeded negative case in a temp fixture).
- `TestClientDTONamesExist`.

No frontend test runner is required; the checks run from Go against the source
text, matching the docs guard already used for removed symbols.

## 7. Compatibility & Rollout

- Refactoring `registerRoutes` to iterate a table is behaviour-preserving; the
  bound patterns are identical.
- The manifest and its tests are additive.
- `routePattern` changes only add cases for mounts it did not name.
- `mise.toml` may gain a convenience task, but the test flag is enough.

## 8. Open Questions

- Should the manifest be consumed by the frontend (a generated
  `routes.generated.ts` of constants) rather than only compared to it?
- Is parsing `client.ts` textually robust enough, or should the client build URLs
  through a small typed helper the test can import?
- Should per-method endpoints be recorded too, by refactoring each handler's
  method branch into the table?
- Should the DTO step eventually generate `types.ts` from Go structs, and is that
  worth the churn?
- Where should the checks live so `mise run test` covers them without a special
  flag?
