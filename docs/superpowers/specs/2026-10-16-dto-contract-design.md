# The Go and TypeScript Contract Design

**Date:** 2026-10-16
**Status:** Proposed
**Issue:** gh-183 (the bead LocalRPG-14a.5)
**Epic:** [#152](https://github.com/darkliquid/LocalRPG/issues/152)
**Proposal:** `docs/architecture/quality-review-2026-10-12.md` (F-4, FE-5)
**Scope:** `pkg/gui` and `frontend/src`. No wire change beyond the JSON tags named below.

## 1. Problem

`pkg/gui/types.go` and `frontend/src/types.ts` are two hand-maintained mirrors of one wire
contract. Measured today: **147 exported structs in `pkg/gui` carry JSON tags**, and
`frontend/src/types.ts` declares **199 exported types** (192 interfaces, 7 aliases). Nothing
connects them, so four kinds of drift are silent:

- a JSON tag and its property name disagree, and the client reads `undefined` forever;
- a Go field is absent from the TypeScript type, so the client cannot see what the server sends;
- a TypeScript property has no Go field, so the client reads something that never arrives;
- optionality disagrees, so the client treats a field the server may omit as always present (or the
  reverse).

The project already knows how to guard exactly this: `pkg/gui/testdata/routes.json` is a checked-in
manifest, and `routes_test.go` fails with "route manifest is stale; regenerate with
`go test ./pkg/gui -update-routes`". `docs_catalogue_test.go` does the same for the documentation
index. The DTO layer has had no such treatment.

## 2. Goals

- **One generated manifest of the Go side**, checked in and regenerated by a flag, listing every
  exported struct that carries a JSON tag and the JSON name, Go name and optionality of each field.
- **A TypeScript test that compares the manifest against `frontend/src/types.ts`**, parsed with the
  TypeScript compiler, and fails naming the type, the field and the difference.
- **The pairings proven rather than declared**: a mirror is the TypeScript interface whose property
  set *is* the Go field set. Where that resolution is not exact, the difference is either fixed or
  recorded, never assumed.
- **Every Go DTO accounted for**: paired, or listed as not mirrored with the reason. A new DTO
  cannot be added without an entry.
- **Reaching zero in this change**, because a check that is red is not a gate. Every difference the
  check finds is fixed or recorded with a reason.
- **One rule with the teeth in the dangerous direction**: a field the server sends that TypeScript
  cannot see, a property that never arrives, and TypeScript requiring what Go may omit are all
  failures; the reverse, TypeScript being defensive about a field that is always sent, is a
  difference that must still be decided, because it hides where the truth lies.

## 3. Non-goals

- **Generating `frontend/src/types.ts` from Go.** The two files are not a 1:1 mapping and should not
  be: the TypeScript side carries discriminated unions (`TurnSegment.kind`), view models with no Go
  counterpart (`SortOption`, `SaveErrorBody`), and comment-carrying types a generator would replace
  with the Go doc comments. A generator would also own a file the frontend reads more than the
  backend does. The manifest checks the mirror; it does not own it.
- **Validating responses at runtime.** F-5's schema-validation recommendation is a separate proposal
  and a separate cost per endpoint.
- **Giving every inline request body a named type.** The client builds some request bodies inline
  with no named TypeScript type; this change records that as a decision per DTO rather than
  refactoring 18 call sites. The list is the follow-up work.
- **The wire format itself.** No field is renamed or removed. Where Go gains `omitempty` it is to
  make an existing, tolerated absence explicit.

## 4. Design

### The manifest

`pkg/gui/dto_manifest_test.go` walks the package's own source with `go/parser` and writes
`pkg/gui/testdata/dto.json`: for each exported struct with at least one JSON tag, its name and its
fields, each as `{json, go, optional}`. Optional means the tag carries `omitempty` or the field is a
pointer, which is exactly what the reference implementation computes.

No hand-written registry: the manifest is generated from the source, so it is complete by
construction and cannot fall behind the structs it describes. `go test ./pkg/gui -update-dto`
rewrites it, and the failure message says so, in the same words as the route manifest.

### The comparison

`frontend/src/test/dtoContract.test.ts` reads the manifest and, for each entry, resolves the mirror:
the TypeScript interface whose property names are exactly the manifest's JSON names. It then fails on:

| The difference | Why it is a failure |
|---|---|
| a JSON name the interface does not declare | the client reads `undefined` for a field the server sends |
| a property with no JSON name, unless recorded in `TS_ONLY` | the client reads a field that never arrives |
| TypeScript required where Go has `omitempty` or a pointer | a field the server may omit is treated as always present |
| TypeScript optional where Go always sends the field, unless recorded in `WIRE_REQUIRED` | the client cannot tell a field the server promises from one it may drop |
| no interface whose property set matches, unless the DTO is in `NOT_MIRRORED` | the mirror does not exist, which is a decision, not an accident |

The two exception lists are in the test, each entry with a reason, and the test fails on an entry
that names a type or field no longer in the manifest, so neither list can rot. The pairings
themselves are not a list: the property-set match is the proof, and a rename on either side breaks
it.

### What the measurement already found

Run before the check was written, over the 113 obvious pairs: **101 agree exactly**, and the
remainder are the reason the check exists:

- **Thirteen optionality disagreements**, all one way: Go requires the field, TypeScript declares it
  optional (`GameSummary.thumbnail_url`, `GenerateCharacterRequest.system_id`/`world_id`/`name`,
  `ImportResultDTO.trust`, `PendingCheck.request`, `TurnSegment.duration`,
  `SystemDetail.rules_prompt`/`character_creation`, `SystemDraftInfo.calls`/`oracle`,
  `TTSInspectResponse.speech_cues`, `WorldDetail.lore_prompt`).
- **Seven Go fields absent from TypeScript**: `CreateSystemRequest.strict`,
  `TestProviderResponse.failure`, and `Turn`'s `speaker`, `dialogue` and `engagement`.
- **Four TypeScript properties with no Go field**, of which `Turn.negotiations` is deliberate: the
  client holds pending negotiations locally and appends them.
- **Eighteen Go DTOs with no TypeScript counterpart**, mostly request bodies the client builds
  inline and responses it reads through a narrower type.

Each is decided in the implementation: a request DTO the client may omit a field from gains
`omitempty` in Go, a response field the server always sends loses its `?` in TypeScript, a field the
client cannot see is declared, and the genuinely deliberate ones are recorded with their reason.

## 5. Behaviour

- A renamed JSON tag, a renamed property, an added field on either side, or a changed `omitempty`
  fails a test that names the type and the field.
- A new Go DTO is in the manifest the moment it is written, so the TypeScript side cannot be
  forgotten: either the mirror exists or the DTO is recorded as not mirrored with a reason.
- Nothing in the running application changes, except that a field that was silently `undefined` is
  now declared, and a request field that was silently sent as `""` may now be omitted.

## 6. Testing

- **The Go side**: the manifest test itself, plus a test that the walk finds a known struct and a
  known field, so a broken parser fails loudly instead of writing an empty manifest.
- **The TypeScript side**: the comparison test, plus a test that a seeded difference is reported —
  the scanner is exercised against a fixture, as `TestFrontendPathScannerFlagsAnUnknownRoute` does
  for routes.
- **The exception lists**: a test that an entry naming a type or field absent from the manifest
  fails, so an allowance cannot outlive what it allowed.
- `mise run test`, `mise run lint`.

## 7. Rollout

One pull request, three commits:

1. The Go manifest and its generator.
2. The TypeScript comparison and its exception lists.
3. The differences resolved — the Go tag changes, the TypeScript declarations, and the reasons.

## 8. Risks

- **A check that reports forty differences at once is unlandable.** The exception lists are the
  pressure valve, but each entry is a decision with a reason rather than a silencer, and the lists are
  checked for staleness so they cannot become a dumping ground.
- **The property-set match can pair a type with the wrong interface** when two interfaces share a
  property set. That is harmless: if the sets are equal, the check's conclusion is the same whichever
  one it names. It becomes harmful only if a wrong pairing hides a difference, which the per-field
  comparison on the named interface would still report.
- **Optionality is a judgement**, not a fact: Go's `omitempty` says the encoder may omit a zero value,
  which is not always the same as "the client may omit it". The two exception lists are where those
  judgements live, and they say which way the truth runs.
- **The TypeScript file is large and hand-maintained.** The check makes drift visible; it does not
  make the file smaller, and the 18 inline request bodies remain the follow-up work.
