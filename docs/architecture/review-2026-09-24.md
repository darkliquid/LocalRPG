## 1. System shape

LocalRPG is a single Go binary exposing three front-ends over one engine:

- **Desktop GUI** — Wails v3 native window by default; when `$DISPLAY`/
  `$WAYLAND_DISPLAY` are unset, or `--headless`/`--socket` is passed, the same
  handler is served over a `0600` Unix socket; `--port N` opts into
  `127.0.0.1:N`.
- **TUI** — Bubbletea via `localrpg play`.
- **CLI/daemon** — one-shot commands plus the HTTP API.

Content is separated into three on-disk tiers resolved by `core.PathResolver`:
`systems/` (mechanics), `worlds/` (lore), `games/` (campaigns, each with a
disposable `cache/index.db`). The engine is deliberately schema-agnostic: RPG
state is opaque YAML plus sandboxed JS/Wasm hooks. That decision is the source of
the codebase's strongest property — nothing hardcodes HP/mana/classes — and of
one recurring cost: features that need to reason about state do so through
opaque `state.Raw()` maps.

Reading the table:

- **Leaves** (`entity`, `core`, `config`, `trace`) have low instability and high
  fan-in. This is healthy and should be preserved: new vocabulary belongs here
  only if it is genuinely shared. `pkg/provider` and `pkg/telemetry` (both
  upcoming) are **new leaves** with fan-in and near-zero fan-out by design.
- **Hubs** (`engine`, `harness`, `media`, `storage`) carry the instability
  pressure. `harness` at 0.50 with 7/7 is the most balanced and is where the
  provider registry and context-plan work lands.
- **Edges** (`gui`, `cmd`, `tui`, `export`) are legitimately unstable; they are
  allowed to depend on everything.
- No import cycles exist in the current graph (the build is `precise`, and no
  cycle findings were reported).

### Hotspots

Top incoming-call functions: `(*FileSink).Event` / `(*Memory).Event` /
`(*StderrLogger).Event` / `(multiLogger).Event` / `(nopLogger).Event` (47 each —
the five `trace.Logger` implementations), `(*Store).GetEntity` (44),
`(*PathResolver).GameDir` (35), `writeJSON` (33), `OrNil` (31),
`(*ConfigManager).Get` (25), `Slugify` (25).

Two observations: the `trace.Logger` interface is the single most-invoked seam in
the program (which is exactly why the OTel bridge can attach without touching
call sites), and `(*Store).GetEntity` being second confirms the assembler reads
the index heavily per turn — the working-set design is aimed at that.

## 3. Layering and seams

The intended direction is `cmd → {gui,tui,cli} → engine → {harness,media,tools,
storage} → {entity,state,config,core}`. The graph respects it.

Well-placed seams, worth keeping:

1. **`trace.Logger`** — a flat `Event(name, fields)` interface, nil-safe via
   `OrNil`, threaded everywhere by `SetLogger`/`*WithLogger`. It is the model to
   copy for any new cross-cutting concern.
2. **`harness.ModelProvider` + optional capability interfaces** — the
   implementation seam for LLM providers.
3. **`media.TTSClient/STTClient/ImageClient` + optional capability interfaces** —
   the same pattern for media.
4. **`storage.Pool` + `storage.OpenGameStore`** — the only sanctioned way to open
   a game database; legacy retirement and shared-handle lifetime live behind it.
5. **`engine.Timeline`** — the single writer of the three layers a turn touches.

Suspicious seams:

1. **`gui.Service` is the whole API surface** in one type (~2700 lines). Its
   fan-out is 14 packages; every endpoint is a method. This is the largest
   locality risk in the codebase. It is not urgent, but the provider-catalogue
   endpoint will add to it, and a split into domain services (game, media,
   settings, catalogue) behind the existing `server.go` routes is the natural
   next structural refactor.
2. **`cmd/localrpg` wires everything by hand**, and `gui.go`/`play.go` duplicate
   that wiring. A `pkg/app` composition root would remove the drift risk as
   OTel, the provider registry, and context strategies each add a dependency.

## 4. Persistence and invariants

- `games/<id>/cache/index.db` is opened only through `storage.OpenGameStore`,
  which returns pooled shared handles. `history.jsonl` is canonical and
  append-only; `index.db` mirrors it and is disposable.
- Guardrail held today: the index can be rebuilt by `Timeline.EnsureIndexed`
  replaying `history.jsonl`. Two upcoming changes test this:
  - `turn_contexts` (full prompt + context) is exact-but-disposable; the compact
    provenance now stored on each history record keeps the log authoritative.
  - `working_set` is authoritative behavioural state, so it must be rederivable
    from history (the continuity plan does this on `EnsureIndexed`). This is the
    most important invariant to police in review.
- `Timeline.RecordTurn` writes notes before the log so a record never points at a
  missing note; an index failure is repaired later. Keep this ordering.

## 5. Turn pipeline end-to-end

```
POST /api/game/{id}/turn  (NDJSON stream; 409 while a turn is in flight)
  └─ Service.BeginTurn → engine.TurnOrchestrator.ProcessAction
       ├─ load history; handle /undo, /gm
       ├─ evaluate Roll dice or a JS action hook
       ├─ ContextAssembler.Assemble  (10 ranked sections → token budget)
       ├─ runGenerationLoop          (bounded tool rounds)
       │    └─ Router.GenerateForRole("gm") → provider (stream)
       │         └─ tools.Executor.Execute on each tool call
       ├─ ResolveEntityMentions / dialogue segments
       ├─ Timeline.RecordTurn        (single writer: notes → log → index)
       ├─ onTurnEnd hooks
       └─ (detached) Chronicler.Regenerate every N turns
```

Cross-cutting touch points the upcoming specs rely on:

- **Context** — `ctx` already flows through every stage, so OTel spans and the
  `TurnContext` provenance both attach without re-plumbing.
- **Continuity** — the assembler is the only place sections are composed; the
  working set and strategy selection belong there, not in the orchestrator.
- **Writer discipline** — any new per-turn persistence (context snapshot, working
  set) must go through `Timeline.RecordTurn` to keep single-writer semantics.

## 6. Provider model

Capabilities are currently declared three times: Go interfaces (discovered by
type assertion in `pkg/gui`), the live `POST /api/tts/inspect` endpoint, and a
515-line frontend `providerPresets.ts`. The approved provider-capability spec
replaces this with a leaf `pkg/provider` registry, self-registering provider
packages, derived capabilities, facades that keep existing factories stable, and
a `GET /api/providers` catalogue the UI renders from. The Gemini session/cache
hooks (`SessionProvider`, `ContextCacher`) are gated on the same capability
vocabulary.

## 7. Context and continuity

The assembler composes rules, lore, instructions, canon, summary, recent, recall,
retrieval, catalogue, and action, ranked so the least essential is trimmed first.
The chronicler regenerates a lossy summary every N turns. What is absent: typed
provenance, a durable context artifact, and any carried-forward working set. The
approved spec adds `TurnContext` (refs + sections + strategy), a persistent
working set rederived from history, and provider-aware strategies that prefer
server sessions/cached prefixes while keeping `history.jsonl` canonical.

## 8. Observability

`pkg/trace` is a bespoke JSONL sink with a two-level redactor, consumed by the
GUI Debug panel. It is payload-rich but uncorrelatable. The approved OTel spec
adds spans (turn/context/provider/tool/storage/media), a metrics catalogue,
`log/slog`, automatic SQLite (`otelsql`) and HTTP (`otelhttp`) instrumentation,
and a bridge that keeps the JSONL sink working. Default is off; OTLP/gRPC to a
local collector when enabled.

## 9. Frontend

`frontend/src/api/client.ts` is the only fetch layer and mirrors `server.go`
routes; `types.ts` mirrors the Go DTOs. The settings UI is the largest component
(`SettingsStudio.tsx`, ~2800 lines) and encodes provider knowledge the backend
should own. The provider-capability work moves that knowledge behind
`/api/providers`. The mirror rule (update `Service`, `server.go`, `types.ts`,
`client.ts` together) is enforced by convention, not tooling; a generated route
manifest would remove the drift risk.

## 10. Concurrency and lifecycle

- Turns are serialised per campaign by `Service.BeginTurn`; a second turn gets
  `409` with `Retry-After`. Nothing persists for a cancelled/disconnected turn.
- `storage.Pool` owns shared handles; `Close` on a shared store is a no-op, which
  is why only `Pool.Close` may close them.
- Background work (summariser, model downloads, playback) is detached; each has
  its own trace events. The OTel provider shutdown must not block on detached
  work, hence the bounded flush.
- Wails webview calls Go directly (no TCP); the socket server unlinks stale
  sockets on start. Both routes reach the same `ServeHTTP`, which is why the
  inbound `otelhttp` wrapper covers all three transports at once.

## 11. Testing

Strengths: stdlib-only tests, `t.TempDir()` for real filesystems, in-memory
provider fakes, and a `trace.Memory` sink that makes observability testable.
Migration, timeline, extraction, and provider tests are thorough.

Thin spots: no tests pin the frontend↔backend route/DTO contract (only
`tsc --noEmit`); the `gui.Service` surface is exercised route-by-route rather than
as a contract; and there is no test that the index is fully rebuildable from
history after arbitrary writes. The OTel, provider, and continuity plans each
add contract tests (drift guard, route decode, replay/repair), which is where the
coverage gains are concentrated.

## 12. Cross-cutting concerns

- **Errors** — wrapped with `%w`; typed sentinels where callers must branch
  (`ErrTurnInFlight`, `ErrGenerationStalled`).
- **Config** — `LOCALRPG_CONFIG_DIR` → XDG → `~/.config/localrpg`, with
  `./localrpg.yaml` merged on top. `gui.NewService` has a documented `--dir`
  twist. Providers resolve shared Gemini keys uniformly, now including the LLM
  test path.
- **Secrets** — `trace.Sanitize` plus `trace.RegisterSecret`; OTel must route
  payloads through the same redactor (the spec requires it).
- **Security** — `ProtectCrossOrigin` wraps handlers in the standard library's
  cross-origin protection; cross-origin browser writes get `403`. The Unix socket
  is `0600`.

## 13. Findings and prioritised refactors

### P0 — already spec'd; do these in the agreed order

1. **Observability** — no spans, metrics, or query/HTTP visibility; the only
   debug surface is an uncorrelatable JSONL file. Spec:
   `2026-09-24-opentelemetry-instrumentation-design.md`; plan written.
2. **Provider capability model** — three drifting sources of truth; UI is
   name-driven. Spec: `2026-09-24-provider-capability-model-design.md`; plan
   written.
3. **Turn context and continuity** — no provenance, no working set, no session
   support. Spec: `2026-09-24-turn-context-and-continuity-design.md`; plan
   written.

### P1 — structural, not yet spec'd

4. **Split `gui.Service`** into domain services behind the existing routes; it is
   the single largest locality risk and every new endpoint grows it.
5. **Introduce a composition root** (`pkg/app`) so `gui.go`, `play.go`, and the
   daemon share one wiring path instead of three hand-maintained ones.
6. **Protect the rebuildability invariant with a test** that mutates a campaign,
   deletes `index.db`, replays history, and asserts the index and working set
   match. This is the invariant most likely to be broken by the P0 work.

### P2 — hygiene, revisit after P0

7. **Split oversized files**: `orchestrator.go` (~987), `context.go` (~868),
   `extractor.go` (~571), and the frontend `SettingsStudio.tsx`. Each is a
   "too many responsibilities in one file" signal.
8. **Generate the route/DTO manifest** so `server.go`, `types.ts`, and `client.ts`
   cannot drift.
9. **Audit detached background work** (summariser, downloads, playback) for
   shutdown ordering once OTel flushes are in the path.

## Appendix B — SQLite schema and access

Tables: `entities`, `edges`, `turns`, `turn_entities`, plus FTS5 virtual tables
`entities_fts`, `turns_fts` and their triggers. Access is concentrated in
`pkg/storage/store.go`, `turn.go`, and `fts.go`; the FTS reads use `bm25` ranking
and `snippet`. Upcoming tables: `turn_contexts`, `working_set`.

`OpenDB` applies pragmas `_journal_mode=WAL&_busy_timeout=5000&_foreign_keys=on
&_synchronous=NORMAL`, which is what lets the GUI, TUI, and an extraction pass
share one file; `migrate` retires legacy columns (e.g. `audio_refs_json`).
